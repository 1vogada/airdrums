# What the scouts checked before the council met

Facts marked "checked" were tested by the scout in that run; "from reading" ones were not.

## The chart site (Chorus Encore)

### What it means for the site

- Song lookup can be a real search-as-you-type box straight on Chorus Encore: the last word matches as a prefix and an artist name alone lists their songs. Wait about 700 ms after the last keystroke, ask for 20-25 charts a page, drop stale answers, and offer 'more' with page+1 until a page comes back with fewer charts than asked.
- The site has to turn charts into songs itself: de-duplicate rows by md5, group charts by normalised artist + title (songId is always null), show one row per song with its versions behind it, and choose the default version with its own ranking (the existing fit() idea: exact title, original artist, lyrics present, pro drums). Hide or label whole-album charts (longer than about 15 minutes or '(Full Album)'), covers, '(Live)', '(6 Fret)' and '(2x Bass Pedal)'.
- Because typo and accent handling is weak, a 'nothing found' answer should trigger automatic second tries before telling the user: strip accents and trailing apostrophes, drop the last word, or search the title alone and filter the artist locally. Results are not ordered by popularity, so the client's own ranking decides what comes first.
- A library row can be rich without loading the chart: album art, title, artist, album, year (take the first four digits), genre, length (prefer notesData.effectiveLength), drum tier 0-6, which levels exist with note counts, notes per second as a 'how busy' figure, charter, source game (packName), and badges for lyrics (means automatic line-up is possible), five-lane, double bass pedal.
- A home screen needs no typing: the advanced search gives ready-made shelves such as 'Rock Band's own songs' (charter exactly Harmonix: 2,337, sortable by name, artist, year, length), 'easy first songs' (maxIntensity 1: 316 Harmonix charts), by genre, by decade (minYear / maxYear), by length, and 'newly added' (search "*").
- Liked songs, history and results should store a slim record per chart keyed by md5 (about 400 bytes: md5, name, artist, album, year, genre, charter, length, drumType, delay, albumArtMd5, tier, levels) and never the raw row (3-70 KB). A whole liked list can be refreshed in one advanced-search call with hash = comma list of md5s; keep name + artist + charter as a fallback in case an md5 disappears after a charter re-uploads.
- Anything that looks up many songs at once (for example matching Spotify's Liked Songs, one search per song) must be queued at well under 50 requests per 30 seconds, cached in the browser, resumable, and must treat 429 and 5xx as 'wait and retry'; the rate-limit headers cannot be read from page script.
- Album art must be lazy-loaded into fixed-size boxes with a fallback tile on error: pictures are full size (up to 2.8 MB, 2000 px) with no thumbnails, so only rows on screen should load them; an <img> shows them despite the octet-stream content type.
- Learning mode can be built on real song parts: effectively every chart names its sections (median 13 per song, about 15 s each). That supports a section list and timeline, jump to a part, loop one part or a run of parts, slow manual-clock practice per part, per-part accuracy on the results screen and 'practise your weakest part'. This only works fully in the silent manual-clock mode or with Spotify seeking, since Spotify's speed cannot change.
- Section names need a clean-up step: strip <tags>, turn underscores into spaces, Title Case, expand 'gtr' to 'Guitar', number repeated identical names, and fall back to 'Part 1..N' for ugc_section names, empty names or charts with three or fewer sections. Merge or skip sections with no drum notes or shorter than about 6 seconds when building practice loops.
- Section times must ride on the same shift as the notes (already done in the working tree's loadChart) and on any later lyric or by-ear correction. A practice loop should start at the marker itself (it may sit half a beat before the bar on a pickup) and can borrow the bar and beat lists for a count-in; do not assume a section starts on a bar line.
- Sections are only known after the notes file is loaded (2-3 range requests, about 100 KB), so the library list cannot show them; load on opening a song and cache the parsed chart or its sections per md5 in IndexedDB so a liked song opens instantly and offline-ish.
- The 'real kit' advantage is wider than Harmonix: 24 of 39 real-kit .mid charts in the sample came from other Rock Band style charters. Whether a chart has them is only known after loading, so remember it per md5 and prefer such a version afterwards, instead of trusting the charter name alone.
- Easier levels cannot be relied on for learning: about 40% of charts are expert only (visible up front in noteCounts). A learning mode needs its own simplification (for example bass drum and snare only, then add hi-hat) and should offer the chart's easier levels only when the search result says they exist.
- Section parsing, a library module and a clock module already exist uncommitted in the repo's working tree (written by another process around 01:14); the build step should read js/chartparse.js, js/charts.js, js/library.js and tests/sections_check.mjs as they are now and build on them instead of starting from the last commit.

### Dead ends

- Getting sections from the search API: no result field carries them (hasSoloSections is only a flag for guitar-style solo markers). They exist only inside the notes file.
- Letting the API group versions of one song: songId is null and groupId is just minus chartId on every row, so there is no server-side grouping to use.
- Sorting by popularity or 'best known first': there is no play count, download count or rating in the result; sort types are only name, artist, album, genre, year, charter, length, modifiedTime.
- Small album-art thumbnails: only the original file exists at files.enchor.us/<albumArtMd5>.jpg (up to 2.8 MB); Cloudflare image resizing (/cdn-cgi/image/...) answers 404.
- Reading X-Ratelimit-Remaining in the browser to pace requests: the headers are sent but not exposed to cross-origin script.
- Asking for more than 250 charts in one request: 400 'Getting more than 250 results at a time is not supported'. And big pages are heavy anyway (uncompressed, up to 70 KB a row).
- Relying on the server's typo tolerance or accent folding for multi-word queries: 'foo fighers' and 'fo fighters' return nothing, 'motorhead' and 'Motörhead' are separate result sets.
- Looking a chart up by chartHash: returned 0 rows for a hash copied from a live result; use hash (md5) or trackHash instead.
- Searching by year in the plain search box: year is not one of the matched fields ('nirvana 1991' only matched a title containing 1991); year filtering needs the advanced endpoint's minYear / maxYear.
- A playable song preview from the API: preview_start_time is only a position in milliseconds. The website's preview player streams the whole .sng package including its audio, which this project must not do.
- Using the audio inside the chart packages (song.opus and the per-drum stems drums_1..4.opus) for slow-down practice or a backing track: technically they sit in the same range-readable file, but it is copyrighted audio and the project's rule (and the comment at the top of js/charts.js) is that the audio is never fetched. I did not fetch any.
- Assuming every section starts on a bar line: 18% do not (pickups, up to half a beat early), so snapping loops to bars would cut the first notes of a part.
- Treating the charter name 'Harmonix' as the only sign of real-kit notes, or assuming easier levels exist: both are false for a large share of charts and can only be confirmed per chart.

## Spotify's Web API

### What it means for the site

- Song lookup must not depend on Spotify. Spotify search is capped at 10 results per call, the dev-mode quota is unpublished and can lock the app out for many hours, and the build cannot be tested with a real account. Make the chart source (api.enchor.us) the primary search that always works, logged in or not, and treat Spotify as an optional enrichment: cover art, exact duration, track URI, and a Play-on-Spotify button.
- If Spotify search is used: type=track, limit=10, debounce typing (about 400 ms or search on Enter), abort the previous request, cache results per query in memory/IndexedDB, never fire one Spotify search per library row. Keep id, uri, name, artists, album.images, duration_ms, external_urls.spotify per result; extend track() in js/spotify.js to keep uri.
- 'Press play and it starts on my Spotify' is buildable with the scopes already granted: GET /me/player/devices, pick the active device or else the first non-restricted one, then PUT /me/player/play?device_id=... with {uris:[uri], position_ms:0}; the existing Follow poll then picks the song up. Handle three failures as plain UI states, not errors: devices is empty or 404 NO_ACTIVE_DEVICE ('Open Spotify on your phone or PC, then press play again' plus an 'Open in Spotify' link to https://open.spotify.com/track/{id}); 403 (Premium needed, or Premium lapsed on the app owner's account, or account not on the app's user list: the current message 'needs spotify premium' is too narrow); 429.
- Because play/seek/pause are Premium-only and Premium can no longer be read from GET /me, the UI cannot know up front whether Play will work: try it and fall back. The silent manual clock and 'follow whatever Spotify is playing' must stay as first-class paths, since they are the only ones that work without Premium and the only ones testable headless.
- Liked: build the site's own liked list in localStorage/IndexedDB as the core feature (works with no Spotify at all, testable with fake key presses). Offer 'Import my Spotify Liked Songs' as an opt-in extra that adds scope user-library-read. Pages are 50 tracks, so a 2,000-song library is 40 Spotify calls: fetch once, on demand, cache in IndexedDB with a manual refresh button, and stop on 429. Matching each liked song to a drum chart is a separate load on Chorus Encore (one enchor search per song): do it lazily for visible rows or in a slow throttled queue with cached answers, never 2,000 calls in a burst.
- Adding scopes means one re-link. Store the granted 'scope' string and an 'authorised_at' time with the tokens in keep(); when a feature needs a scope that is missing, show 'Link again to let the site read your Liked Songs' instead of failing with 403. Ask for all wanted scopes in one go (suggested: the three current ones + user-library-read, and user-read-recently-played only if a 'recently played on Spotify' shelf is really built) so the owner re-links once.
- Add invalid_grant handling now regardless of new features: refresh tokens die 6 months after login (enforced since 2026-07-20). On 400 invalid_grant, call unlink(), show 'Spotify login expired, link again', and fall back to the manual clock. Today the site would loop on an error with linked() still true.
- Cut the polling. The site asks currently-playing every 2 s for as long as a play page is open; a developer reports hitting the new per-account quota at 3 s polling. The Follow class already keeps a steady extrapolated clock, so it can poll every 2 s only for the first few answers after a song starts or after a user action (play, seek, restart), then every 5-10 s, slower still when paused, and not at all when the tab is hidden or no play page is open. Read the 429 body: on reason QUOTA_EXCEEDED or a long Retry-After, stop polling, tell the user, and switch to the manual clock rather than waiting silently (the current code waits Retry-After with no cap and no message change).
- Learning mode cannot slow Spotify down (no speed control in the Web API or the Web Playback SDK). Slow practice has to run on the site's own clock: the silent ManualClock at 50-100% tempo, ideally with the site's own click/metronome or synth drum guide (js/synth.js exists), plus section looping. With Spotify at full speed, learning tools are limited to loop-a-section (PUT /me/player/seek back to the loop start, Premium only, with about a second of jitter per seek) and waiting/count-in; design the loop feature to work on the manual clock first and treat Spotify looping as a bonus.
- Refactor js/spotify.js so one request helper covers every endpoint: base https://api.spotify.com/v1, JSON body with Content-Type, parsed error body (status, message, reason), distinct outcomes for 401, 403, 404 NO_ACTIVE_DEVICE, 429 rate vs quota. Route all calls through one injectable fetch so the headless tests can stub Spotify responses shaped like the documented ones (search paging object tracks.items[], saved tracks items[].track, devices[], 204 for play/seek/pause, the 404 and 429 bodies).
- Policy awareness for wording and scope: Spotify's Developer Policy says not to create a game with the Spotify Platform and not to synchronise recordings with visual media. For a private 5-user Development Mode app that only reads what is playing and remote-controls the user's own Spotify app this is a wording and risk matter, not a technical block, but it argues for (a) presenting the site as a practice / play-along tool rather than a game, (b) not embedding Spotify audio in the page, and (c) showing Spotify cover art and titles with a link back to the track on Spotify and keeping all of it in the user's own browser.
- Setup page copy should say the facts the owner will trip over: the Spotify app's owner needs Premium for the app to work at all; starting, restarting and looping a song need Premium; each extra person needs to be added under User Management (max 5); the login has to be redone every 6 months and once after this update if they want Liked Songs.

### Dead ends

- Slowing a song down for practice through Spotify: impossible. No speed/tempo parameter on any player endpoint and no rate method in the Web Playback SDK (methods are only connect, pause, resume, seek, volume, next/previous, activateElement). Browser extensions that do it hack the Spotify web player and are not something the site can use.
- Playing Spotify audio inside the page with the Web Playback SDK: technically allowed for Premium users (needs extra scopes streaming, user-read-email, user-read-private, so another re-link), but it adds nothing the learning mode needs (still no speed control, no raw audio for analysis), it relies on DRM (encrypted-media/Widevine) so it cannot be exercised in a headless test browser, it would route the music through the PC instead of wherever the owner listens now, and there is one unanswered 2026 report of player.connect() hanging for a Development Mode app. Not worth building in a one-sitting, untestable release.
- Starting playback when no Spotify app is open anywhere: not possible from the Web API. GET /me/player/devices returns an empty list and PUT /me/player/play returns 404 NO_ACTIVE_DEVICE. The only thing the page can do is link to https://open.spotify.com/track/{id} and ask the user to press play there (the follow clock then takes over).
- Big Spotify search pages or popularity sorting: limit is now max 10 (default 5) and the popularity field is gone for Development Mode, so 'top results by popularity' and 50-per-page search are out. Rely on Spotify's relevance order.
- 30-second preview clips (preview_url) as in-page audio for a song picker or practice: the field is deprecated/removed, and the policy forbids offering previews as a standalone feature.
- Checking 'does this user have Premium?' before showing Play: GET /me no longer returns product for Development Mode apps (removed Feb 2026, marked deprecated). Detect by the 403 on the first play/seek instead.
- Batch lookups (GET /tracks?ids=...) to enrich many library rows in one call: removed in February 2026; only GET /tracks/{id} one at a time remains, which would burn the unpublished quota. Store the metadata you already got from search / saved tracks instead.
- Getting out of the limits by applying for Extended Quota Mode: individuals cannot apply since 2025-05-15; it needs a registered business and 250k monthly active users.
- Using the Client Credentials flow so search works without the user logging in: it needs a client secret, which a static site cannot hold and the constraints forbid. Search via Spotify only works after the PKCE login; before login, search must go to the chart source.
- Shipping a shared Spotify client ID with the site so visitors skip the dashboard step: Development Mode caps each client ID at 5 allow-listed users and every user must be added by hand by the owner; the 'bring your own client ID' setup has to stay.
- Verifying any Spotify flow end to end before shipping: needs a real Premium account, a real consent screen and an open Spotify client. Only stubbed-fetch tests are possible, so the live behaviour of play, devices, the 404 body and the missing-scope 403 remains unverified until the owner tries it.

### Dead ends

- Slowing down Spotify: neither the Web Playback SDK nor the Web API has a speed control, so a learning mode below 100% cannot use Spotify's sound at all.
- Loading the CC0 drum kits through jsDelivr: the repos are over its 50 MB limit and some files answer 403. Only raw.githubusercontent.com or a copy in the site's own repo works.
- The sample URLs most web demos use (Tone.js audio, smplr's drum machines, oramics/sampled, Dirt-Samples): they load fine cross-origin but carry no licence, so they are not worth the risk.
- A hidden, tiny or audio-only YouTube player, or notes drawn over the video: forbidden (200 x 200 minimum, no overlays, no player that is not shown, no separating audio from video).
- Finding a YouTube video for a song automatically: needs a Data API key; the keyless search embed was shut down in November 2020. The user has to paste a link.
- Fine tempo steps on YouTube: the player only takes its own list of rates and rounds anything else toward 1.
- Slowing a user's file with AudioBufferSourceNode.playbackRate: it drops the pitch with the speed. Only the media element stretches time at the same pitch.
- Telling the site's own guide drum from the learner's hit by timing when both come out of speakers in the same room: they land within the same few tens of milliseconds.
- Layering the synth guide over Spotify at 100%: the Spotify line-up is good to about 0.2 s, far too loose for two drum sounds to sit together.
- Checking by ear before shipping: no browser, speaker or microphone is available to the builder; only numbers (rendered buffers, scheduled times) can be checked.
